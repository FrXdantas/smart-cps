O que a ferramenta faz

A ferramenta procura defeitos em programas C, Java e Kotlin com verificação formal. Em vez de executar testes, ela examina todos os caminhos do programa até um limite e, quando acha um defeito, mostra a execução que leva até ele (o contraexemplo).

  1. Você escolhe uma pasta com os arquivos-fonte.
  2. O ESBMC (para C) ou o JBMC (para Java e Kotlin) verifica cada arquivo.
  3. Cada defeito encontrado recebe uma categoria CWE e a regra CERT correspondente.
  4. Se quiser, um modelo de linguagem propõe um conserto. O conserto só é aceito depois que o verificador roda de novo e confirma que o defeito sumiu.

Primeira verificação: um arquivo simples

Crie uma pasta com este programa em C. O laço vai até i <= N e lê uma posição além do fim do vetor.

#define N 5
int notas[N] = {7, 8, 6, 9, 10};

int main(void) {
  int soma = 0;
  for (int i = 0; i <= N; i++)   /* deveria ser i < N */
    soma += notas[i];
  return soma / N;
}
  1. Em Nova verificação, clique em Enviar pasta, ao lado do campo da pasta, e escolha a pasta do seu computador. Rodando sem Docker, também dá para digitar o caminho direto no campo.
  2. Coloque unwind em 6 ou mais. O laço dá 6 voltas e o defeito está na última; com 5, o verificador não chega até ela e o resultado sai SAFE.
  3. Clique em Verificar. O resultado esperado é BUG, CWE-125 (leitura fora do vetor).
  4. Clique na linha do arquivo, na tabela de alvos, para ver o contraexemplo: a linha do defeito, a condição que falhou e os valores das variáveis até ali.

A pasta exemplos/ do repositório traz este caso (c/notas.c) e um em Kotlin (kotlin/Media.kt, divisão por zero com a lista vazia, CWE-369).

Uma pasta com vários arquivos

Cada arquivo é um alvo e é verificado separado, a partir do main. Um arquivo C sem main sai como ERROR, e uma classe Java ou Kotlin sem main sai como SEM MAIN. Para verificar esses arquivos, indique uma função de entrada ou junte os arquivos (veja Opções de projeto).

Medir acerto com gabarito

Se os arquivos estiverem em pastas chamadas com_bug e sem_bug (também valem bug/safe), a ferramenta compara o resultado com o gabarito e calcula a pontuação CASTLE, além de precisão e revocação.

Como ler os resultados

StatusO que significa
BUGO verificador achou uma execução que viola uma propriedade. Há contraexemplo.
SAFENenhuma violação até o limite escolhido (unwind). Não é prova para qualquer tamanho de entrada.
UNKNOWNO limite não cobriu algum laço (estratégia sound ou k-induction). Aumente o unwind.
TIMEOUTO tempo acabou antes da resposta. Aumente o timeout ou reduza o unwind.
ERRORO verificador não conseguiu analisar o arquivo (por exemplo, header ausente, ou C sem main).
COMPILE_FAILJava ou Kotlin que não compilou. Clique na linha para ver o erro.
SEM MAINClasse Java ou Kotlin sem ponto de entrada. Não é erro: não há o que verificar sozinha.

Nas colunas, CWE é a categoria do defeito no catálogo MITRE e CERT traz a prioridade (P1 a P27) e o nível (L1 é o mais urgente). CASTLE só aparece quando há gabarito (pastas com_bug/sem_bug).

Opções da verificação

Estratégia
Como os laços são tratados.
  • bounded (padrão): desenrola cada laço até o unwind. Rápido, mas SAFE só vale até esse limite.
  • sound: se o unwind não cobrir um laço, o resultado é UNKNOWN em vez de SAFE.
  • incremental-bmc: aumenta o unwind sozinho até achar o defeito ou acabar o tempo. Bom quando você não sabe quantas voltas o laço dá.
  • k-induction: tenta provar o laço por indução, sem desenrolar tudo. Pode dar UNKNOWN.
incremental-bmc e k-induction existem só no ESBMC (C). Em Java e Kotlin, o JBMC usa bounded.
unwind
Quantas voltas de cada laço são examinadas. Valor maior acha defeitos mais fundos, mas gasta mais tempo e memória. Típico: 5 a 20.
timeout (s)
Tempo máximo por arquivo. Valor maior reduz os TIMEOUT em casos difíceis; valor menor corta cedo os casos pesados. Típico: 30 a 120.
jobs
Quantos arquivos são verificados ao mesmo tempo. Mais jobs termina antes, mas usa mais CPU e memória. Use 1 em casos pesados (por exemplo, com concorrência).
solver
O resolvedor usado pelo ESBMC. boolector é o padrão e o mais rápido; z3 costuma ir melhor com aritmética pesada. A lista mostra só os que estão instalados. O JBMC usa o próprio resolvedor.
Propriedades opcionais
Desligadas por padrão. Ligue só quando procurar esse tipo de defeito.
  • Overflow unsigned: acusa estouro em size_t e unsigned (CWE-190), como em cálculo de tamanho de alocação. O estouro com sinal é sempre verificado. Fica desligado porque muito código usa a volta do unsigned de propósito (hash, buffer circular).
  • Concorrência: procura corrida de dados (CWE-362) e impasse (CWE-833) entre threads pthread. Deixa a verificação bem mais lenta.
  • NaN em ponto flutuante: acusa operações que geram NaN, como 0/0 ou infinito menos infinito (CWE-682, regra FLP32-C).

Opções de projeto

Ficam em Menu > Opções de projeto. Servem para verificar parte de um projeto maior sem compilar o projeto inteiro. Para arquivos simples, deixe tudo vazio. Quando alguma estiver definida, ela aparece escrita abaixo dos parâmetros, e clicar nesse texto também abre as opções.

Pastas de headers (-I)
Pastas onde estão os .h que o arquivo inclui, uma por linha. Sem elas, o verificador para com erro de análise antes de começar. Funções externas sem código são tratadas como caixas-pretas, por isso não é preciso compilar o projeto.
Arquivos verificados juntos
Lista de .c que formam um programa só, um por linha, com o do main primeiro. Exemplo: repl.c e tinyexpr.c. Sem isso, cada arquivo é verificado sozinho e as funções dos outros viram caixas-pretas, o que esconde defeitos entre arquivos.
Função de entrada (--function)
Verifica uma função específica como se fosse o main. Os argumentos recebem qualquer valor possível, então não é preciso escrever um programa de teste. Útil para firmware e bibliotecas, que não têm main. Vazio usa o main.

Guia do reparo

O reparo usa um modelo de linguagem para propor a correção e o verificador para julgá-la. Ele aparece abaixo dos resultados quando a run tem pelo menos um BUG.

1. Configurar o modelo

  1. Abra Menu > Configurar LLM (o mesmo botão aparece no quadro do reparo).
  2. Escolha o provedor: DeepSeek, Groq, OpenRouter, Local (Ollama, roda na própria máquina e não precisa de chave) ou Personalizado.
  3. Cole a chave da API e escolha o modelo. A chave fica só no seu navegador; o servidor não a grava em disco.

Para ver o funcionamento sem gastar saldo, ligue dry-run: o laço roda, mas sem chamar o modelo, e o código volta inalterado.

2. Reparar

  1. Clique em Reparar bugs. Cada alvo com BUG passa pelo laço abaixo, até 5 tentativas.
  2. O modelo recebe o código, a CWE, a regra CERT e o contraexemplo, e devolve o arquivo corrigido.
  3. Antes do verificador, o conserto passa por guardas que recusam truques: apagar ou reescrever a asserção que falhava, acrescentar assume, ou tornar o trecho do defeito inalcançável.
  4. O verificador roda de novo com a mesma configuração da run (unwind, timeout, solver, estratégia e propriedades). Se o defeito continuar, o novo contraexemplo volta para o modelo na próxima tentativa.

Só os que faltam, ligado por padrão, pula os alvos já reparados num reparo anterior da mesma run. O botão Parar encerra depois da tentativa em curso e mantém o que já foi reparado.

3. Ler o resultado de cada tentativa

VeredictoO que significa
FIX_OKO verificador confirmou que o defeito sumiu. O alvo fica como REPAIRED.
STILL_VULNERABLEO mesmo defeito continua. Nova tentativa com o novo contraexemplo.
DIFFERENT_BUGO conserto trocou um defeito por outro.
INVALID_PATCHRecusado pelas guardas, sem chegar ao verificador.
PROVIDER_ERRORO provedor do modelo recusou a chamada (limite de uso, 429). Não conta como falha de reparo.
TIMEOUT / ERRORA reverificação não terminou ou não compilou.

Clique num alvo do reparo para ver a trilha das tentativas e o código original ao lado do corrigido. Um FIX_OK prova que aquele defeito sumiu até o limite usado; vale revisar o conserto antes de aplicá-lo, porque mudar uma constante, por exemplo, pode passar sem corrigir a lógica.

Baixar e exportar

  • SARIF: os achados no formato aberto lido pelo VS Code, pelo GitHub e por CI, com a configuração exata da run e, quando houver, o conserto verificado.
  • Baixar pasta: um .zip com os arquivos originais e os corrigidos ao lado, com o sufixo _FIXED. Pela seta ao lado, dá para baixar só os originais.
  • Exportar relatório (.md): resumo do reparo em texto, com a trilha de cada alvo.
  • Histórico: cada run mostra a data, a pasta e o modelo usado no reparo (ou "sem reparo"; quem acha o defeito é o ESBMC ou o JBMC, o modelo só entra no conserto). Clique numa run para reabrir o relatório; apagar remove a run e a pasta dela no servidor; Recolher esconde a lista, e a escolha fica guardada no navegador.

Limites conhecidos

  • SAFE vale só até o unwind escolhido. Um defeito mais fundo pode passar.
  • Projetos C++ grandes, que usam muito a biblioteca padrão, podem não ser processados pelo ESBMC. Prefira C ou unidades pequenas.
  • A conversão para um inteiro menor que não cabe no tipo (o truncamento em ponto fixo, como em Q15) ainda não é detectada: em C ela não é erro para o verificador.
  • Estouro e NaN em ponto flutuante usam a CWE-682 (cálculo incorreto), porque não existe CWE própria para eles. A regra CERT diferencia: FLP03-C para estouro, FLP32-C para NaN.
  • Em Java e Kotlin, coleções como ArrayList e HashMap podem gerar alarmes até em código correto.
